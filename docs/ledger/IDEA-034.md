## D1 — User decision (2026-10-11)

Our goal is maximum profit, so a strategy arm that loses money must never be rated SUPPORTED, under any registration. The current behaviour (a treatment losing 2% against a baseline losing 5% is SUPPORTED) is a regression, not a deliberate choice.

D1 rests on our own objective, which all of these support. It does not need the score to be pure profit.

## Investigation: why the condition was dropped

1. **Origin.** `e9e3671` (author `wtvlol` <keithchiawk@…>, i.e. Keith; 2026-10-10 18:44 +0800, "feat: add offline strategy risk accounting and research fixtures") introduced `evaluate()` with `"SUPPORTED" if low > 0 and absolute_mean > 0 else "NOT_SUPPORTED" if high < 0 or absolute_mean <= 0 else "INCONCLUSIVE"`, where `absolute_mean` is the treatment's own mean return, and with service costs always subtracted. Its only economic test (`test_paired_costs_negative_edge_and_missing_allocations`) has a worse but profitable treatment, so the absolute condition was never exercised by a test.
2. **Reviews that preceded the rewrite.** IDEA-030 R12.7 (static review) described the rule as "hardcodes after-service-cost incremental returns and a positive lower-bound/positive absolute-mean test". Its defect was that registered free-text criteria (`paired_metric`, `kill_rule`, `inconclusive_rule`) were accepted but ignored; the remedy asked for was "either reject unsupported structured criteria or calculate exactly the registered rule". IDEA-026 RV01 (owner Keith, reviewer Yao Zhu) says the same. Neither says the absolute condition is wrong or should go.
3. **Removal.** `cfa3f02` (author `Cookiemunchrr` <songyaozhu@…>, i.e. Yao Zhu's git identity, co-authored by Claude Opus 5.5; 2026-10-10 21:01 +0800, "… structured economic registration … (IDEA-031 stage 5)") rewrote the verdict for EconomicRegistration.v2. The structured fields mirror the v1 text fields plus a margin (`metric`, `margin`, `support_rule`, `kill_rule`, `inconclusive_rule`); the only support rule was `LOWER_BOUND_ABOVE_MARGIN`. The `absolute` list, the `absolute_mean > 0` condition and the `treatment_absolute_mean` report field were deleted.
4. **No record of a decision.** The commit message lists what became structured and says nothing about the absolute condition. AC-E05 (IDEA-031) does not mention absolute return. IDEA-031's AC-R01 table of changed test expectations has one economic row ("v1 free-text criteria → v2 structured; v1 → NOT_RUN", reason "R12.7 ignored criteria"). No ledger entry, PR comment or SKILL item between 2026-10-10 and the 2026-10-11 code review discusses dropping it. The first record of the loss is IDEA-033 R24 (2026-10-11).

**Root cause: accidental.** "Evaluate exactly as registered" was implemented by enumerating the v1 text criteria as structured fields. The absolute condition was a hardcoded extra with no v1 text field behind it, so it had no place in the schema and was dropped with the old code. No test covered it, so nothing failed. R24 restored the reporting and added an opt-in rule but left the default unsafe.

## Design (decided here, 2026-10-11)

1. **Mandatory absolute condition, lower bound.** SUPPORTED requires, under every support rule: the paired lower bound above the registered margin (unchanged) **and** the bootstrap lower bound of the treatment's own net return above zero, using the same resampled clusters, the same confidence level and the registered metric's net (after service costs when the metric says so). Why the lower bound, not the mean: SUPPORTED is a confidence statement; with the mean rule a treatment whose own return is a coin flip around a small positive mean (e.g. −1%/+3% per cluster) would be SUPPORTED as "making money" without evidence that it does. Judging both conditions the same way keeps the verdict's meaning consistent. Cost: absolute returns carry the market move that pairing cancels, so the absolute bound is wider than the paired one and more experiments will be INCONCLUSIVE; INCONCLUSIVE keeps the registered default, the conservative outcome. The two bounds are marginal, not a joint confidence region; together they are stricter than either.
2. **How a losing-but-better treatment is reported.** If the upper bound of the treatment's own return is at or below zero (it confidently does not make money): **NOT_SUPPORTED**, reason `TREATMENT_ABSOLUTE_NET_NOT_POSITIVE`. Under D1 the hypothesis "this arm is worth adopting" is then confidently false, whatever the paired difference, so the mandatory absolute condition has a kill side as well as a support side, and it applies in addition to the registered paired kill rule. If the treatment's own interval spans zero and the paired rule would support it: **INCONCLUSIVE**, reason `TREATMENT_ABSOLUTE_LOWER_BOUND_NOT_POSITIVE`. Otherwise the registered paired rules decide as before. This supersedes R24's choice of INCONCLUSIVE for a confidently losing treatment (`83f4ddc`), which treated the absolute check as optional. Either way the registered default is kept and nothing is promoted; the difference is whether the question is answered.
3. **The R24 opt-in rule is removed**, not aliased. `LOWER_BOUND_ABOVE_MARGIN_AND_TREATMENT_NET_POSITIVE` used the mean; the mandatory condition is stricter. An alias would let a registration name a mean rule and be judged by a lower-bound rule, the "accepted but evaluated differently" defect of R12.7. As an unsupported value it returns NOT_RUN. It was added in `83f4ddc` on the unmerged PR; no registration or config uses it (checked with `git grep` on 2026-10-11).
4. **Report.** Kept: `treatment_absolute_mean`, warning `TREATMENT_ABSOLUTE_NET_NOT_POSITIVE` (mean ≤ 0). Added: `absolute_return_rule: "TREATMENT_LOWER_BOUND_ABOVE_ZERO"` (so each report states the rule it applied), `treatment_absolute_interval`, `baseline_absolute_mean`, warnings `BASELINE_ABSOLUTE_NET_NOT_POSITIVE` and, under the wallet-only metric, `TREATMENT_NET_NOT_POSITIVE_AFTER_SERVICE_COSTS`. The paired bootstrap draws the same clusters in the same order as before, so every paired interval is unchanged.

- 2026-10-11 note (IDEA-033 R26, wtvlol's PR #7 review): design 1's lower-bound rule assumed the percentile interval comes from enough resamples. A registration could ask for 1 draw, and then the "bounds" are a single resample that can sit above a negative mean (two clusters, treatment −10%/+9%, seed 0: SUPPORTED with a −0.5% mean). Fixed in `ea38a4c`: a registration needs at least 25 draws beyond each percentile bound (`MIN_TAIL_DRAWS`; 1000 at 95%), otherwise NOT_RUN `BOOTSTRAP_DRAWS_TOO_FEW`. SUPPORTED also requires the observed treatment mean above zero and the observed paired mean above the margin; an interval that excludes its own point estimate is INCONCLUSIVE, reason `BOOTSTRAP_INTERVAL_EXCLUDES_OBSERVED_MEAN`. D1 is unchanged and now holds under any registrable draw count. Verification: IDEA-033 V16.
